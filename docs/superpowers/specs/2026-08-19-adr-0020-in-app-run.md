# ADR-0020 in the app — the registered floor was not met

**Runs the protocol registered in
[`2026-08-19-adr-0020-in-app-run-protocol.md`](2026-08-19-adr-0020-in-app-run-protocol.md),
committed before any instrumented launch.** Raw logs:
`docs/superpowers/measurements/adr0020-in-app/`.

**Verdict: the run does not discharge ADR-0020 Decision 5.** Two draws produced **19 reverse
targets and one baseline miss**, against a registered floor of five. Per the protocol's own
wording that is an **inadequate fixture, not a falsified ADR** — and the fixture's inadequacy is
itself the most useful thing the run produced.

## What was registered, and what happened to each claim

| # | Registered claim | Outcome |
|---|---|---|
| 1 | ≥ 5 targets `baseline-unresolved` | **Not met — 1** |
| 2 | ≥ 1 recovers through a widened query | **Not met — 0** (the one miss stayed unresolved) |
| 3 | Full chain observed end to end | **Not met** — no recovery to observe |
| 4 | N = 3 bound observed **binding** (a target with ≥ 4 spellings issuing exactly 3 searches) | **Not met** — the only widened target held exactly 3 spellings, so the cap did not bind |
| 5 | Every recovery classified by arm; fuzzy recoveries hand-checked | **Vacuously met** — all 18 baseline recoveries were `exact`; zero fuzzy recoveries occurred, so nothing needed adjudication |

Claim 4 deserves the emphasis. The one widened target searched **three** spellings and stopped,
which *looks* like the cap working and is not: it held three spellings and spent all three. The
registered wording asked for a target with **four or more**, precisely so that "stopped at three"
would mean something. It is reported as not met rather than waved through on the unit test that
covers the same rule.

## The frame

Asserted before anything was computed from it, per the protocol's scar list:

| | |
|---|---|
| Rows | **19**, from 12 detail pages |
| Unique MAL ids | **19** — no double-count |
| Outcomes | 18 `baseline-resolved`, 1 `unresolved`, 0 `recovered` |
| Arms | 18 `exact`, 1 `none` — **zero fuzzy picks in the entire run** |
| Rows spending the MAL arm's extra request | **1** — exactly the rows that missed |
| Searches per row | 18 rows × 1, 1 row × 3 |

**Two independent draws produced byte-identical target sets.** The first visited 4 detail pages, the
second 12, on a freshly erased container each time — and both logged the same 19 MAL ids. That is
the frame assertion that matters here: the second draw added eight pages and **zero** new targets.

## Why the fixture cannot reach the floor

MAL's recommendations for Home's popular MangaDex titles overlap almost completely, and a resolved
id is cached, so a repeat target never re-searches and never logs. The cohort saturates at 19.

More to the point, **18 of 19 resolved on the first spelling, every one through the exact-`malId`
arm.** Popular titles are exactly the titles MangaDex carries under the spelling MAL leads with.
The offline measurement drew ~10–14% unresolved from a frame built to include tail titles; this
cohort came in near 5%, on a sample of 19, which is consistent with it and says nothing new.

**A cohort that resolves everything cannot exhibit a recovery.** Reaching the floor needs targets
MangaDex files under a different spelling than MAL leads with — which means drawing obscure titles
deliberately, not walking the popular grid.

## What *was* observed, and what it is worth

The single miss exercised every moving part of ADR-0020 except the recovery itself:

```json
{"malId":18161,"outcome":"unresolved","arm":"none","fetchedTitles":true,
 "spellings":["Katanagatari","Katanagatari: Sword Tale","刀語"],
 "searched":["Katanagatari","Katanagatari: Sword Tale","刀語"]}
```

- The baseline search ran and missed.
- **The MAL arm's extra `mangaDetail` fired** (`fetchedTitles: true`) — the request the offline
  measurement's cost column excluded and ADR-0020 corrected 1.76 → 3.09 for. It fired on the row
  that missed and on no other row, which is Decision 2's "paid by rows that missed" rule, observed.
- **The spelling set grew from 1 to 3** — MAL's romaji, English, and Japanese titles — proving the
  fetch returns usable spellings in the app and not just in a harness.
- **Three searches were issued with three different spellings**, in order.

That is the widening machinery running end to end in the app on live network. It is *not* claim 3,
which asks for a chain ending in a recovered card, and it must not be reported as if it were.

`Katanagatari` not recovering is unsurprising and is not evidence against the ADR: it is a light
novel with a limited manga presence, and no spelling will find a MangaDex entry that does not exist.
The offline run measured 25–35% of misses as unrecoverable for exactly this reason.

## Instrument notes

`VerificationSwitches.logReverse` plus a three-line `trace` call inside
`MALReverseResolver.searchWidening`, `#if DEBUG`, gated on `ADR0020_REVERSE_LOG=1`. Unlike
ADR-0019's injected instrument this one is inline, because `searchWidening` resolves up to four
targets concurrently and a wrapper around the `search` closure cannot attribute a query to a target.

**The instrument is sound and is not what failed here.** It logged 19 of 19 targets across two runs
with no gaps and no duplicates, and the one interesting row is fully described.

## The fixture problem this run leaves behind

The seeded simulator was **destroyed during this session** — `xcrun simctl erase` against a wedged
device during unrelated test-bundle debugging, without checking its contents first. Lost:
`works.json` (107 Works, 86 with a MAL id), a 25-entry history, and `upgrade-attempts.json` with its
declared hand edit. No backup exists.

Consequences, stated plainly:

- **The AniList arm cannot be verified in-app until a library and reading history exist again**,
  because the For You pool needs a taste profile. That arm resolves 12 works per refresh and is the
  better instrument for this claim; it is also the arm that costs nothing, so it is the less urgent
  one to watch.
- **The search-width measurement's seed set is not reproducible.** Its committed raw data and
  harness stand, but a future re-run cannot draw the same seeds.
- ADR-0019 Amendment 1 had already said this fixture needed re-seeding before ~2026-08-23, so the
  loss pulled forward work that was scheduled rather than destroying something permanent.

## What the next attempt should do differently

1. **Draw obscure titles deliberately.** Walking Home's grid saturates at 19 targets that MangaDex
   carries. Search for titles whose MangaDex entry is filed under an English name — the offline run's
   own recovered rows (*Mugen no Juunin*, *Kaikan♥Phrase*, *Blood+*, *Cosplay★Animal*) are known-good
   candidates and are already hand-checked.
2. **Clear the reverse cache between draws**, or accept that a repeated target logs nothing. Each
   `xcodebuild test` run gets a fresh container, which happens to do this for free.
3. **Pick a target holding ≥ 4 spellings** if claim 4 is to be met at all. That is checkable against
   MAL before the run rather than discovered after it.
